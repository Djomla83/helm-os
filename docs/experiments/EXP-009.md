# EXP-009: Evidence Loop — the smallest end-to-end proof of concept

**Status:** Planned — not executed.\
**Owner / reviewer:** not assigned.\
**Approved budget:** not set. No new spend without approval.\
**Derived from:** [Foundation audit §9](../research/FOUNDATION_AUDIT.md#s09), which holds the full
rationale. This file is the executable plan; the audit is normative for the reasoning.

## Hypothesis

For a small set of Windows desktop applications, an automated system can produce reproducible,
version-scoped evidence that a specific application build works on a specific runtime build, detect
when a runtime change breaks it, attribute the breakage to one axis, restore the last known-good
state without losing user data, and do so at a per-application maintenance cost that one person can
sustain.

This is the project's actual product thesis. It is not currently supported by evidence, and both
funded incumbents in this space chose to pay humans instead. EXP-009 exists to test it before any
architecture is frozen.

## Preconditions and inputs

Base distribution and version; one physical machine with a named GPU vendor and driver version;
Wine 11.0 and 11.17 builds; three applications that are legally downloadable without an account or a
purchased licence; a second person available for the reproducibility check. None of these may be
invented to make the plan look complete — see [audit §9.3](../research/FOUNDATION_AUDIT.md#s09) for
the full list of missing decisions, which includes the Track A versus Track B question this
experiment informs.

## Procedure

**Gate 0 first — three to five days, no product code.** G0-1 establishes whether the motivating
communication-application problem is a Wine problem at all. G0-2 runs the DirectComposition probe
against vanilla Wine, wine-staging and Proton, deciding whether the Chromium-embedding application
class is in scope. G0-3 is the ten-minute hardlink registry-corruption test. G0-4 runs the incumbent's
existing analysis engine over the target applications to establish the true state of the art. G0-5
runs an escape harness against each shipping sandbox configuration. **Gate 0 results are published
whatever they say.**

**Then the loop**, over three applications with deliberately different oracle classes — one with a
purely deterministic file-output oracle and no GUI automation, one requiring a GUI document-save
workflow, and one probing the hard application class:

```text
identify -> plan -> stage -> install -> verify -> pin
         -> bump one axis -> re-verify -> attribute -> revert that axis -> re-verify
```

Fix versions, hardware, scenarios and expectations before starting. Record every deviation from this
plan in the report. Keep every failed attempt and the reason for every blocked step.

## Positive outcome criterion

All six pre-registered criteria in [audit §9.2](../research/FOUNDATION_AUDIT.md#s09) hold:
reproducibility by a second person with zero undocumented manual steps; a **false-pass rate of zero**
with bounded flake rates against injected breakages; automatic regression detection across a Wine
bump; correct single-axis attribution in at least two of three injected cases; rollback that
preserves a user document byte-identically in ten trials out of ten; and a measured human cost within
the stated ceilings.

## Negative or inconclusive outcome

Any of the five pre-registered failure criteria triggers a written decision rather than a retry. A
non-zero false-pass rate redirects the evidence pillar to version-stamped human attestation. A GUI
oracle that is too expensive or too flaky narrows the public claim to what can be asserted
deterministically. **Any loss or mutation of a user document stops the work entirely** until the
data-safety design in [ADR-0017](../adr/ADR-0017-data-safety-rules.md) is corrected. A
re-qualification cost above the ceiling means HELM cannot be a catalogue at the intended scale, and
the promise must be resized to the staff that exist.

## Limits and safety

One machine, one GPU, one desktop session, three applications, two Wine builds, six weeks, one
person, no new spend. No catalogue, GUI shell, OS image, SDK, virtual machine or AI work is in scope.
No unknown installer is executed on the host. No purchased licence, vendor account or activation is
used, which itself bounds what can be concluded. A result on three applications is not a statement
about any application class, and must not be reported as one.

## Deliverable

A separate `EXP-009-REPORT.md` following the [runbook](../runbooks/EXPERIMENT_REPORT.md), with the
harness source, exact component versions, the recipes, every evidence record including failures and
repeats, the injected breakages and whether each was caught, the measured human-time log, and a
written `supported`, `not_supported` or `inconclusive` verdict on the hypothesis above. Do not fill
this plan in with invented results.
