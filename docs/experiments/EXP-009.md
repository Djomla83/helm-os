## 1. What this experiment is for

HELM's product mission is a free, open-source, user-controlled desktop with reliable application
experiences. Windows compatibility is **one mechanism** toward that mission, not the mission. The
Evidence Loop is a **proposed enabling subsystem**, not a replacement for the product vision, and
Gate 0 does not decide the product.

Gate 0 answers a narrower question: **which of the audit's load-bearing assumptions survive contact
with execution, and which are blocked by the environment we actually have?**

Gate 0 explicitly does **not** authorise implementation, does not accept ADR-0013 to ADR-0019, and
does not by itself justify starting the PoC.

## 2. Outcome vocabulary

Every check resolves to exactly one of these. They are defined here so that no result can be
re-graded after the fact.

| Outcome | Meaning |
|---|---|
| **PASS** | The check ran to completion and the pre-registered expectation held. |
| **FAIL** | The check ran to completion and the pre-registered expectation did not hold. A FAIL is a result, not a reason to retry. |
| **INCONCLUSIVE** | The check ran but the evidence does not decide the question — for example the oracle could not distinguish the outcomes, or the result was not stable across repeats. |
| **BLOCKED** | The check could not run because a required precondition was absent (missing software, hardware, licence, authorised account, or approval). Records the exact unblock condition. |
| **NOT_RUN** | The check was not attempted. Records why. |

**BLOCKED and NOT_RUN are not failures and must never be reported as passes, nor silently omitted.**
Inference is not a substitute for execution: if a check is BLOCKED, its question stays open.

## 3. Recording requirements

No check produces a valid result unless all of the following are captured **at run time**, not
reconstructed afterwards. This list exists because the audit's own comparison found that the
mature incumbent in this space records all of it per job, and HELM should not ship less.

| Class | Must record |
|---|---|
| Application artifact | Vendor, product name, version string, download URL, retrieval timestamp, **SHA-256 of the exact file**, and installer technology. |
| Runtime artifact | Wine or Proton build identity — version, source revision where known, patch set, and packaging origin — plus any staging patch sets enabled. |
| Dependency versions | Every applied verb or component with its version and the digest of anything downloaded. |
| Host configuration | Kernel, distribution, filesystem type of the prefix location, CPU, memory, GPU model and driver version, and whether the session is X11 or Wayland. |
| Display settings | Resolution, scale factor, monitor count, and colour depth — recorded because these change application behaviour and are a known source of irreproducibility. |
| Test-code revision | The git commit of the harness and of the check definitions used for the run. |
| Execution record | Exact commands, exit codes, wall-clock start and end, and every artifact path. |

The environment record for the 2026-09-07 run is
[`evidence/G0-environment-2026-09-07.json`](evidence/G0-environment-2026-09-07.json).

## 5. Controls

Each check that produces a verdict carries both:

- a **known-good control** — a configuration expected to pass, to detect a harness that fails
  everything; and
- a **deliberately broken control** — a configuration seeded with a specific defect, to detect a
  harness that passes everything.

A check whose controls do not both behave as expected is **INCONCLUSIVE**, regardless of what it
reported for the real subject.

## 6. Output validation, not interaction success

A check must assert on **what the application produced**, not on whether an interaction appeared to
succeed. A click that lands, a window that appears and a process that exits zero are not evidence
that the work was done.

Where a deterministic output oracle exists (a file, a digest, an exit code, parsed output), that is
the required oracle. Where only a GUI path exists, the check records that its oracle is weaker and
its verdict carries that limitation explicitly.

## 7. Statistical honesty rules

These are binding on every report produced under this experiment.

1. **False passes are reported with an explicit denominator.** "0 false passes" is meaningless;
   "0 false passes in 20 seeded-defect trials across 3 applications" is a result.
2. **Zero observed false passes is not proof of a zero underlying error rate.** With *n* trials and
   zero observed events, the report states the upper bound implied by the sample size and nothing
   stronger.
3. **False failures, INCONCLUSIVE cases and BLOCKED checks are reported alongside**, never dropped.
4. **Minimum useful scenario coverage is declared in advance** — which user-visible workflows a
   verdict claims to cover — and any verdict is scoped to it.
5. **Every failed attempt is preserved**, with its artifacts, in the report. Re-running a check is
   permitted only as an explicitly labelled repeat; **retrying until green is prohibited**.
6. **Acceptance criteria may not be changed after observing a result.** Changes go in the change
   log in [§9](#chg) with a timestamp preceding the run they govern.

### G0-3 — Are hardlink farms safe as prefix snapshots?

**Revision 1's procedure was invalid and is withdrawn** (audit correction C-9): it compared two
hardlinks to the same inode, which are identical by construction whether contamination occurred or
not, and it inspected the wrong hive for the change it induced.

Corrected procedure, in two independent parts:

- **G0-3a, filesystem mechanics, no Wine required.** Take a **content copy** (not a hardlink) of the
  file as the reference. Then, on a hardlink farm, perform (i) an in-place truncate-and-rewrite and
  (ii) a write-temp-then-rename, and compare each result against the reference copy. Record whether
  the farm copy tracked the live file, whether a zero-length window was observable, and whether the
  filesystem supports reflink copies. *Executed 2026-09-07 — see the report.*
- **G0-3b, Wine behaviour, Wine required.** Repeat against a real prefix, inducing a change that
  lands in the **user** hive as well as the machine hive, and covering the case where the hive is
  opened read-only. This is the part that shows which path Wine actually takes, and it is
  **BLOCKED** without Wine.

Report contamination and corruption **separately**. Contamination requires no fault and is
disqualifying on its own; corruption requires an additional fault and must not be claimed without
inducing one.

### G0-4 — What is the true state of the art in automated environment derivation?

Run the incumbent analyzer over the cohort applications and record, per application: what it
detected, what it suggested, whether suggestions are applied automatically or require confirmation,
whether dependency suggestions are installed or only named, and — the decisive question —
**whether the resulting configuration actually runs the application**.

This check is a **baseline measurement (B1)**, not a competitive demonstration. Its output feeds
the novelty assessment in the audit.

### G0-5 — What does per-application confinement actually contain?

Run a purpose-built probe binary that enumerates and attempts access outside its prefix — host
root, home directory, sibling prefixes, device nodes, the session bus — under each shipping sandbox
configuration, and record the resulting escape matrix.

Use **canary files with synthetic content only**. Never use real credentials, keys or user data.

## 9. Recovery testing safety rules

<a id="rec"></a>

Binding whenever any recovery behaviour is exercised, at Gate 0 or later.

1. **Disposable prefixes and synthetic data only.** No real account, document, key or message.
2. **A mutable hardlink copy is never treated as an independent snapshot** — that is the very
   property under test.
3. **The four recovery layers are tested and reported separately**, because conflating them is how
   a rollback silently destroys user work:
   - runtime rollback (the Wine or Proton build),
   - prefix rollback (application state, registry, installed components),
   - user-document recovery,
   - external and server-side state.
4. **Verify the saved copy is unchanged after the live prefix is modified.** This is the direct test
   of whether the copy is a snapshot at all.
5. **Test whether data created after the snapshot survives the recovery procedure.** A rollback that
   silently discards work created after the restore point is a worse outcome than the fault it was
   meant to repair.
6. **Account activation, credentials and server-side synchronisation are explicit unverified areas**
   unless actually tested with authorised test accounts. **Never bypass licensing or
   authentication**, and never work around an activation limit. If it cannot be tested lawfully with
   an authorised account, it is BLOCKED.
7. **Never publish** installers, credentials, private messages, licence keys or user data. Evidence
   is published redacted, or referenced rather than included.

## 10. Scope and cost measurement

<a id="scope"></a>

### 10.1. Cohort scope

The planned Windows application cohort stays explicit and unchanged: the three PoC slots are a
deterministic-output Win32 application, a GUI document-integrity application, and one hard-class
application gated on G0-2. Any native-application investigation is recorded in its own section and
**is not counted as a Windows compatibility result**.

### 10.2. What is measured

Reported per arm, never collapsed into a single score:

| Measure | Definition |
|---|---|
| Human setup effort | Attended wall-clock minutes, separated from unattended waiting. |
| Intervention count | Manual actions, counted against a written intervention taxonomy fixed before the run. |
| Test-maintenance effort | Time to keep a check working across a runtime bump. |
| Compute and model usage | Machine time, and tokens and cost where a model is used, published alongside the result. |
| Retries and documents consulted | With the caveat that several upstream sources block automated access, so this is not comparable between a human arm and an automated arm without saying so. |

**Operator impression is not evidence of effort.** Published research on developer-productivity
self-report shows forecast and recollection erring in the same direction as each other and against
measurement, so no HELM-versus-baseline claim may rest on how fast it felt.

### 10.3. Agent necessity

**Do not assume an AI agent is needed for every step.** G0-2, G0-3, G0-5 and the static
classification work are deterministic scripting, and the incumbent analyzer demonstrates that the
identify-and-plan step is solved with static analysis and no model at all. The plausibly
agent-shaped work is reading heterogeneous vendor documentation, turning a novel failure log into a
ranked hypothesis, and *authoring* a GUI oracle. Budgeting an agent for every step inflates cost and
weakens the comparison.

### 10.4. Finding classification

Every finding is classified as **correctness**, **automation feasibility**, **user experience**, or
**economics**, and reported under that heading. These do not combine into one number: an approach
can be correct and uneconomic, or cheap and wrong.
